Code walkthrough

Inside the promotion scraper

How run.py --retailer boots --brands Clinique turns into verified rows of competitor pricing — every stage, and the file that owns it.

The shape of it

Roughly 8,100 lines across 24 modules. The split that matters: everything except adapters/ is retailer-agnostic. The seven adapters know about HTML and APIs; nothing else does.

That's not tidiness for its own sake. When Lookfantastic changes its markup — and it did, mid-audit — only one file needs touching.

Stage by stage

1

Read the command, pick the adapter

run.py · adapters/base.py

--retailer accepts a short name or any URL — boots, boots.com, https://www.boots.com/clinique all resolve the same. An unknown site fails loudly rather than guessing selectors.

2

Open the right kind of session adapter

configure_session()

This is where the two retailers genuinely diverge. Lookfantastic serves everything to a plain HTTP request. Boots sits behind Imperva bot protection and returns a challenge page — Pardon Our Interruption — so its adapter asks for a real browser instead.

The framework doesn't know or care which; it just uses whatever session the adapter registered.

3

Find candidate product URLs adapter

product_listing_urls() · select_candidates()

Lookfantastic publishes a sitemap with 16,409 products; filtering it by brand slug costs one request. Boots' sitemap is behind the same bot wall, so its adapter walks brand listing pages instead.

4

Fetch, throttled and robots-aware

Scrapling's SitemapSpider

Retries, rate limiting, robots.txt, URL-level dedup and checkpointing all come from Scrapling. None of it is reimplemented here — that was the point of building on it.

5

Read one page into a Product adapter

extract_product() · extract_campaigns()

The only place raw HTML is touched. See the next diagram for how the fields are assembled.

6

Seven checks, or it doesn't ship

validation.py

A record that fails is written to _rejected.csv with a machine-readable reason — never silently dropped. A rejection usually means the page changed, which is information you want.

7

Deduplicate, attach campaigns

spider.py

Dedup keys on the retailer's own product id, so the same item reached through four different URLs collapses into one record. Campaigns are then linked by id — see below for why they aren't nested.

8

Write JSON and per-brand CSV

output.py

One JSON document holding everything, plus one products CSV per brand for opening in Excel.

Where a price actually comes from

The original version trusted the page title to establish brand and grabbed whatever price string it found nearby. That's how it ended up reporting the 125 ml SKU on the 200 ml product.

Three independent sources now feed one record, each chosen because the retailer maintains it as data rather than as presentation:

Why the breadcrumb? It links to the retailer's own brand taxonomy page. A URL slug or a page title is marketing copy — a Clinique page mentions six other brands in its recommendations. The breadcrumb is the retailer stating, in its own filing system, what this product is.
Where the category comes from. Neither retailer puts one on the product page — Lookfantastic's breadcrumb is brand-shaped, and Boots leaves its category variable empty in served HTML. The category exists only in the retailer's listing structure, so --resolve-categories reads those listings as a lookup table and fills the field in after the crawl. A listing that redirects off its category (asking for Clinique fragrance lands on Clinique view-all) is discarded rather than trusted — otherwise all 46 Clinique products get filed as fragrance.

Products and campaigns are joined, not nested

The obvious design is to nest products inside their campaign. It breaks on real data three ways, all of which occur on Lookfantastic today.

Asking what a whole site is promoting

Drop the brands entirely and the same pipeline answers a different question:

python run.py --retailer boots --campaigns-only

No products are fetched. It reads the retailer's offers hub and returns every campaign advertised there, each with the page it was advertised on.

RetailerCampaignsScopes
Lookfantastic166 brand · 3 category · 7 sitewide
Boots262 category · 4 sitewide · 20 unresolved
John Lewis—no central offers hub; promotions are per brand
Why Boots leaves 20 unresolved. It puts brands and departments in the same URL slot — /no7/… and /fragrance/… are indistinguishable by shape. Claiming a brand there would invent campaigns that don't exist, so the scope says unresolved instead. Lookfantastic's URLs separate /c/brands/ from /c/health-beauty/, so its scopes can be asserted.

Two details this mode depends on, both found by running it rather than reading the HTML:

Boots challenges the first request of any session — and the challenge response is what sets the cookie. So the run fetches the homepage first purely to be rejected, discards it, and the offers hub then returns 1.3 MB instead of a 6 KB block page. Those requests are chained, not queued together; running them concurrently lets the hub go out cold.

An offers page is mostly navigation. The permissive offer test used for product banners treats "gift finder", "gift cards" and "free next day delivery" as promotions, which is fine in a slot the retailer reserves for offers and useless when scanning a whole page. Campaign discovery uses a stricter test that requires a concrete mechanic — a percentage, a bundle, a code, a spend threshold, an explicit gift-with-purchase.

Changing what counts as an offer

The offer vocabulary is a file, not code. Point a run at one and only those keywords apply — the built-in retail rules switch off rather than combining:

python run.py --retailer boots --brands Clinique \
    --offer-keywords keywords/black-friday.txt

Replacing rather than extending is the point: you can read the file and know exactly what the run will match. The effect is measurable on Lookfantastic's offers hub — the built-in rules find 17 campaigns, a betting vocabulary finds 0, because none of its wording appears on a beauty retailer.

Each keyword is a regular expression, so bet .* get and [0-9]+x wager work as written, while a plain phrase gets word boundaries so bonus doesn't match bonuses. A broken pattern stops the run and names the keyword — a typo that silently matched nothing would look exactly like a site running no promotions.

The seven checks

A record has to clear all of them. Each rejection names itself, so _rejected.csv tells you what went wrong rather than just that something did.

reasonCatches
missing_titleNo product name could be read
missing_priceNo current price could be read
invalid_discountWas-price below the now-price — an impossible pair
discount_mismatchAdvertised "40% off" disagrees with the two prices
unverified_brandBrand couldn't be proved from the retailer's own data
brand_mismatchVerified brand isn't one you asked for
variant_conflictSKU belongs to a different product than the URL

Adding the third retailer

The architecture's claim is that a new retailer touches one file. Concretely, subclass RetailerAdapter and implement four things:

@register
class JohnLewisAdapter(RetailerAdapter):
    name = "johnlewis"
    domain = "www.johnlewis.com"

    def configure_session(self, manager):   # HTTP, or a browser?
    def product_listing_urls(self, brands): # where the products are
    def extract_product(self, response):    # page → Product
    def extract_campaigns(self, response):  # page → Campaign[]

Nothing outside that file changes. Validation, dedup, campaign linking, matching, history and output all work on the new retailer the moment it returns records.

One rule, learned the hard way: inspect the real HTML before writing a single selector. Check for schema.org JSON-LD first — where it exists, most of the extraction is already done and far more stable than anything you'd write against CSS classes.

Before you change anything

.venv\Scripts\python.exe run_tests.py -q

Five suites, no network, about two seconds. They run against captured real pages, so they catch extraction drift as well as logic errors. Green before you start and green after you finish means you didn't break what was working.
